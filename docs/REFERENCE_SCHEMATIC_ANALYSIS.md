# Findings from the real KiCad schematic comparison

## Evidence

The reference supplied for analysis was generated by Eeschema 9.0 (`version 20250114`). The project's generated sample was emitted by SKiDL 2.3.0 with `version 20230409`. They are different S-expression schema revisions, so the reference is useful for field-placement conventions but is not a byte-for-byte template to copy.

## Finding 1 — explicit field coordinates conflict with `fields_autoplaced yes`

The generated component instances contain `(fields_autoplaced yes)`. The post-processing pass also rewrites the `Reference` and `Value` property coordinates to hand-selected positions. These directives conflict: KiCad can recompute automatically placed fields when opening the schematic, which is consistent with the screenshot where labels are placed on top of symbols instead of at the coordinates written by post-processing.

The reference schematic's symbol instances use explicit per-instance property coordinates and do not include `fields_autoplaced yes` in the examples supplied. The first correction therefore sets `fields_autoplaced` to `no` wherever the post-processor writes explicit field positions.

This is a targeted fix, not yet a general collision-free layout engine. `_field_targets()` still uses heuristics based on symbol class and rotation. A future layout pass must inspect symbol geometry and neighboring text, wires, and symbols.

## Finding 2 — duplicated coincident `power:VS` instance

The generated sample contains two instances of `power:VS` at exactly `(151.13, 99.06, 0)`, each with its own UUID and power reference. In a flat schematic, two identical global power symbols coincident at the same coordinate are redundant. The post-processor now removes subsequent instances with the same power `lib_id`, origin, and rotation while preserving symbols at different locations and different power names.

This workaround prevents the redundant instance from appearing in the final file. A later integration test should still verify whether the duplicate is produced by the selected SKiDL version and whether an upstream correction is available.

## Finding 3 — power-symbol instance path differs from the sheet root

In the generated sample, the root sheet UUID is `60f19bb6-11e5-4216-807b-2f92590677fd`, and ordinary component instances use that UUID in their `(instances ...)` path. The two `power:VS` instances instead refer to `/218b5f90-a139-55d3-a988-331ecbe7ee0c`. The flat-output post-processor now rewrites power-symbol paths to the actual root sheet UUID for consistency.

This normalization assumes the current backend's `flatness=1.0` output. It must be revised if hierarchical schematic generation is introduced.

## Verification limits

Automated unit tests verify the textual transformations, explicit field coordinates, power-symbol de-duplication, and flat instance paths. They do not prove that KiCad renders the result correctly or that electrical connectivity is unchanged. Those claims require opening the generated file in the target KiCad version, exporting a netlist, and running `kicad-cli sch erc` against golden fixtures.
